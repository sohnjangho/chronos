## 왜 (기획서의 중심축)

스케줄의 본질: **일정은 약속이고, 매 순간 바뀐다. 같은 크기의 변동도 어느 작업이 바뀌었느냐(CPM)에 따라 약속에 주는 영향이 다르고, 변동이 쌓이면 관리 포인트(크리티컬·크리티컬 직전)가 옮겨 간다. 옮겨 간 포인트를 놓치면 약속이 늦어진다.**

시너지 문장: **CPM 이 "어디를 지켜봐야 하는지"를 정하고, Liner 가 "그곳에 무슨 일이 생길지"를 근거와 함께 찾아온다.**

지금 코드에는 포인트 이동 계산이 있다(`backend/app/core/delay.py` 의 `critical_added`·`critical_removed`) — 그러나 지연 영향 카드의 정보 줄로만 보이고(`frontend/src/programs/chat/cards/DelayImpactCard.tsx`, `delays/DelayDetail.tsx`), **포인트 → 바깥 위험 확인 → 담당자 연락**으로 이어지지 않는다. 이 계획이 그 고리를 닫는다.

## PM 이 정한 것

- 붙인다: **① Search API Premium Data**(`knowledge` 표 — 날씨 예보·평균, 원자재·환율 등) · **④ Search Agent API**(본문 인용이 출처 문장 `referenceChunks` 에 이어진 답).
- 붙이지 않는다: Decisions API(확률 판정이 틀리면 영향이 크다), Credits API(의미 적음).
- Premium Data 는 **관리 포인트에만** 겨냥해 쓴다(일반 근거 검색은 지금처럼 `include_knowledge:false`).

## 만들 것

### A. 관리 포인트 계산 (코드 — 판단 없음)
- 버전이 바뀔 때(승인·반영·되돌리기·실적 기록·Data Date 변경)와 지연 분석 때, 그 일정의 **관리 포인트**를 계산해 버전별로 남긴다.
- 관리 포인트 = 아직 끝나지 않은 액티비티 중
  1. 크리티컬, 그리고
  2. 크리티컬 직전: 전체 여유(TF) ≤ **k 근무일**(설정값, 기본 3 — 상수 금지, 설정 또는 개발 콘솔에서 바꿀 수 있게),
  3. 보는 창: Data Date 부터 **w 주**(설정값, 기본 3 — 3주 룩어헤드와 맞춤) 안에 시작·진행하는 것.
- 앞 버전과 견줘 **바뀐 것**을 낸다: 새로 들어온 포인트(새 크리티컬 · 여유가 k 이하로 줄어든 것), 빠진 포인트, 여유가 줄어든 양.
- 날짜·여유는 모두 기존 엔진(`core/cpm.py`·`calendar.py`·`resources.py`)이 낸 값. LLM 은 이 계산에 관여하지 않는다.

### B. 바깥 위험 겨냥 검색 (Liner)
- 새로 들어온 포인트(기본 최대 **5개**, 설정값)마다:
  1. **무엇을 찾을지 정하기** — LLM(light)이 액티비티 이름·WBS·주요 자원·분야만 보고 `weather_sensitive`(실외·타설·양중 등), `supply`(걸린 자재·업체 이름)를 뽑는다. 날짜는 쓰지 않는다(코드가 그 액티비티의 ES~EF 를 붙인다).
  2. **날씨** — `weather_sensitive` 이면 Search API web 을 **`include_knowledge` 켠 채로** 「{현장 주소의 시·군} {ES~EF 기간} 날씨 예보」류로 부르고, 응답 `knowledge[]`(`title`·`description`·`sources`·`dataAsOf`·`columns`·`rows`)에서 그 기간의 강수 확률·강수량을 읽는다. 현장 주소는 「프로젝트 관리」의 `site address` 값(비어 있으면 날씨 검색을 하지 않고 「현장 주소가 없어 날씨를 보지 않음」).
  3. **자재·업체** — `supply` 가 있으면 MCP `search_business` 로 그 업체·자재의 납기·공급 소식.
  4. 결과는 기존 근거 표(evidence)에 출처와 함께 남긴다. **예보는 30일 재사용 규칙에서 빼고 짧게**(기본 6시간, 설정값) — 낡은 예보를 다시 쓰지 않게.
- 숫자를 지어내지 않는다: `knowledge` 가 없거나 그 기간 값이 없으면 「바깥 자료 없음」으로 두고 숫자를 쓰지 않는다. Premium Data 의 숫자는 **표시와 근거로만** 쓰고, 일정에 넣으려면 사람이 [조건으로 넣어 보기] → 조건·규칙 미리 보기(작업 금지 기간) → 승인함을 거친다. 자동으로 일정을 바꾸지 않는다.
- **0단계 실측 먼저** (실제 Liner, 호출 몇 번): 한국 시·군 이름으로 `knowledge` 에 날씨 예보 표가 오는지, 기간이 며칠까지인지, `country_code`·`lang` 을 받는지. **오지 않으면** 날씨는 기존 기상청 도구(`tools/data/weather.py`, 3일 예보)로 대신하고 Premium Data 는 원자재·환율 표(자재 단가 위험)로만 쓴다 — 결과를 진행 기록에 남기고 PM 에게 알린다.

### C. Search Agent 로 근거 문장 붙이기 (Liner)
- `POST /agents/search`(`mode` general/scholar, `stream:false`) → `answer` + `references` + 출처 문장 `referenceChunks`.
- 쓰는 곳 두 군데:
  1. 관리 포인트 카드의 위험 한 줄마다 [근거 문장 보기] — 그 위험을 뒷받침하는 출처 문장.
  2. 만회안·조건 변경 승인 건의 근거 — 법규·기준을 묻는 근거(예: 야간 타설 허용 시간, 동절기 타설 기준)에 출처 문장을 붙인다. 지금의 `evidence.search`(링크 목록)는 그대로 두고, 「문장까지」가 필요할 때 Search Agent 를 부른다.
- 30초 안팎 걸린다(p50 30초·p99 100초, 상한 300초): 대화·카드를 막지 않고 **뒤에서 채운다**(「근거 문장 찾는 중」 → 채워짐). 실패는 HTTP 200 안의 `data-error` 로도 온다 — `[DONE]` 만 보고 성공 처리하지 말 것(`01_대회정보/라이너_기능_조사.md` 6절 8번).
- 답 본문을 그대로 사실로 쓰지 않는다: 화면에는 **출처 문장과 링크**를 보이고, 에이전트가 그 문장에 없는 숫자를 말하면 기존 근거 대조 규칙으로 막는다.

### D. 관리 포인트 카드와 행동
- 카드 내용: 「관리 포인트가 바뀌었습니다」 · 새 포인트(액티비티, 여유 n일 → m일, 크리티컬 여부) · 바깥 위험 줄(날씨: 「04.15~04.17 강수 확률 70% · 출처 · 기준 시각」, 업체: 소식 한 줄 · 출처) · [근거 문장 보기] · 단추 [담당자에게 확인 연락] [만회안 보기] [조건으로 넣어 보기](날씨일 때).
- [담당자에게 확인 연락] → 기존 연락처 흐름(`notify.draft_message`·`notify.draft_call`)의 초안으로 이어진다. 담당자는 그 액티비티의 담당 협력사·주소록에서 고르게 하고(자동 발송 없음), 질문에는 포인트와 바깥 위험을 넣는다. 연락 하네스(시험 모드·근무시간·권한·번호 비공개)는 그대로 적용.
- 나오는 곳: ① 에이전트 대화의 카드(변동을 말한 대화에), ② 「주의할 일정」(`programs/attention`)에 포인트 수·바뀜 표시, ③ 공정률의 위젯 하나(선택).
- **화면은 만들기 전에 시안 1~2개를 PM 에게 먼저 보인다**(PM 규칙). 시간이 없으니 기존 카드 꼴(`DelayImpactCard` 등)을 따르는 시안 하나로 빨리 확인받는다.
- 에이전트 도구: `points.check`(지금 포인트와 바뀐 것, 바깥 위험 포함 — 읽기). 지침에 「변동을 반영한 뒤에는 관리 포인트를 확인하고, 바뀌었으면 카드를 낸다」.

### F. 당김 효과 확인 (꼭 — 계산은 코드만)
- 입력: 이동 묶음 — ① 만회안(A·B) 묶음, ② 만약에 복사본, ③ 말로 한 요청 "〔작업〕을 n일 당기면?"(그 액티비티 od 를 n 만큼 줄임, 최소 1, 관계는 그대로, 실적 있는 액티비티는 불가 — `core/shorten.py` 규칙과 같게).
- 계산: 기존 엔진만 쓴다 — `core/shorten.py` 의 `apply_moves` → `level`(자원 맞춤까지) → 넣기 전·뒤 준공. 새 판단 없음.
- 출력:
  - **당긴 일수 vs 준공에 반영된 일수**(예: 「골조 5일 당김 → 준공 1일 당겨짐」).
  - **다음에 약속을 정하는 줄**: 넣은 뒤의 크리티컬 사슬 중 이번에 건드리지 않은 부분(액티비티 이름 순서, 예: 「커튼월 도면 승인 → 커튼월 제작 → 커튼월·외장 패널」). 그 액티비티들이 관리 포인트인지 표시.
  - 반영 비율이 설정값(`accel_warn_ratio`, 기본 0.5 — 상수 금지) 아래면 경고 줄 「당긴 n일 중 m일만 준공에 반영됩니다」.

  3. 카드의 「다음 결정 줄」 작업 → [관리 포인트로 보기](바깥 위험·담당자 연락 흐름 D 와 같은 카드).
- 시연: 씨앗 「5층 사무동 신축」에서 **골조를 당겨도 준공이 거의 안 당겨지고 다음 줄이 커튼월 쪽**인 경우를 Task 2 스크립트를 넓혀 찾는다(골조 각 액티비티 n=1~5 당김 × 결과). 없으면 씨앗을 고치지 말고 PM 에게 묻는다(커튼월 선행에 「도면 승인」류 액티비티가 씨앗에 없을 수 있음 — 있는 이름으로 장면을 맞춘다).
- 시험: 크리티컬 하나만 당김 → 준공 같은 만큼 / 병렬 경로가 곧 막는 경우 → 일부만 / 자원 맞춤에 막힌 경우(`level`) / 실적 있는 액티비티 거절 / 비율 경고 경계 / 다음 줄 계산이 넣기 전 크리티컬과 같으면 「같은 줄」.
- 화면은 기존 카드·비교판 꼴을 따르고, 시안은 Task 6 시안과 함께 PM 에게.

### G. 관리 포인트 준비 상태 점검 (여유가 되면 — 기존 기능 잇기)
- 관리 포인트 작업 중 시작이 Data Date 부터 `points_ready_days`(기본 10 근무일, 설정값) 안인 것에 카드 단추 [준비 상태 확인 요청] → 기존 FieldHub D-3 핸드오프 점검 항목(선행 작업면·자재 반입·장비·인력)을 그 작업에 만들고 담당자 연락 초안(D 와 같은 길)으로 잇는다. 자동 발송·자동 생성 없음 — 사람이 누른다.
