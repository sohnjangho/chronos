## 0. 한 장 요약

> **「일정은 매 순간 바뀐다. 무엇이 약속을 늦추는지는, 바뀔 때마다 다시 정해진다.」**

같은 3일 지연이라도, 여유가 있는 작업이면 약속(준공)에 아무 일이 없고, 약속을 정하는 줄에 있으면 약속이 3일 늦어진다. 그리고 변동이 쌓이면 **약속을 정하는 줄 — 관리 포인트 — 이 다른 곳으로 옮겨 간다.** 사람은 마지막으로 본 크리티컬 패스를 계속 지키다가, 옮겨 간 포인트를 놓친다. 그 자리에서 약속이 늦어진다.

ChronOS 는 변동이 들어올 때마다 이 한 바퀴를 쉬지 않고 돈다.

```
변동 → 영향을 잰다(코드) → 관리 포인트를 다시 짚는다(코드) → 그곳의 바깥 위험을 찾는다(Liner)
     → 담당자에게 확인한다(Liner 글 + AI 전화) → 사람이 결정한다(승인함) → 새 버전에서 다시
```

> **CPM 이 "어디를 지켜봐야 하는지"를 정하고, Liner 가 "그곳에 무슨 일이 생길지"를 근거와 함께 찾아온다.**

| 한눈에 | |
|---|---|
| 시연의 핵심 숫자 | 같은 「공장 제작 3일 지연」 두 건 — 하나는 변화 없음, 하나는 관리 포인트 3건을 새로 만듦 · 그 뒤 「골조 5일 당김」은 준공을 **1일**만 당긴다(지연 전에는 4일) |
| Liner API | **7가지** — Router(모델) · Search · Search Premium Data · Search Agent · MCP(법령·업체) · Visualization · Embeddings |
| 만든 것 | 앱 18개의 일정 OS(PC·태블릿·폰) · 결정론적 일정 엔진 · 4겹 하네스 · 승인함·버전 · 문자·AI 전화 · 개발 콘솔 |
| 검증 | 서버 시험 〔갱신〕건 · 화면 시험 〔갱신〕건 통과 · 실제 Liner 46단계 업무 시나리오 · 실제 통화 시험 통과 |

## 1. 문제 정의 (30%) — 약속은 어디서 늦어지나

### 1-1. 스케줄의 본질

1. **스케줄은 약속이다.** 마지막 날짜는 발주처·고객·팀과 맺은 약속이다.
2. **스케줄은 매 순간 바뀐다.** 날씨, 자재, 사람, 설비, 고객 요구 — 건설이든 생산이든 연구개발이든 같다.
3. **같은 변동도 영향은 위치에 따라 다르다.** 여유(Float)가 있는 작업의 3일 지연은 약속에 영향이 없고, 크리티컬 패스 위의 1일 지연은 약속을 1일 늦춘다(CPM).
4. **변동이 쌓이면 관리 포인트가 옮겨 간다.** 어제 여유가 있던 작업이 오늘 크리티컬이 된다. 크리티컬 패스는 고정된 선이 아니라 변동마다 다시 그려진다.
5. **옮겨 간 포인트를 놓치면 약속이 늦어진다.** 그리고 엉뚱한 곳에 힘을 쏟는다.

〔그림: 같은 네트워크에 같은 3일 지연 두 건 — 왼쪽은 여유에 흡수, 오른쪽은 약속을 정하는 줄이 바뀜. "크기가 아니라 위치가 약속을 늦춘다."〕

> **쉬운 용어** — 크리티컬 패스: 하루 늦으면 마지막 날짜도 하루 늦는 작업 연결선 · 여유(Float): 마지막 날짜를 밀지 않고 늦출 수 있는 일수 · 관리 포인트(ChronOS): 크리티컬이거나 여유가 3일 이하인, 앞으로 3주 안의 작업

### 1-2. 만든 사람이 겪은 장면

> 골조가 크리티컬이었다. 야간 작업까지 넣어 골조를 앞당겨 끝냈다.
> 그런데 다음 외장 작업을 시작할 수 없었다. 그사이 커튼월 공장 제작이 늦어져, **약속을 정하는 줄은 이미 커튼월 쪽으로 옮겨 가 있었다.**
> 골조를 당기느라 쓴 돈과 사람은 준공을 하루도 당기지 못했다.

15년 동안 4,200억~3조 원 규모의 건설·플랜트 현장에서 일정을 맡으며 가장 자주 본 실패는 "몰라서"가 아니라 **"포인트가 옮겨 간 것을 늦게 알아서"** 생겼다. 힘을 쏟기 전에 "지금 약속을 정하는 줄이 어디인가"를 다시 봐야 한다 — 그러나 변동마다 사람이 그것을 할 수는 없다.

### 1-3. 사람이 놓치는 네 가지 까닭

| 까닭 | 지금의 모습 |
|---|---|
| 변동마다 전체를 다시 계산할 수 없다 | 공정표는 주간 회의 때 손으로 고친다 |
| 계산해도 "지금 어디를 봐야 하나"를 매번 판단할 수 없다 | 처음 정한 크리티컬 패스를 계속 본다 |
| 포인트를 알아도 그곳의 바깥 위험을 따로 찾아야 한다 | 자재값·환율·업체 사정은 담당자의 감에 맡긴다 |
| 담당자에게 바로 확인할 수 없다 | 전화를 돌리고, 통화 내용은 남지 않는다 |

### 1-4. 기존 도구로 안 되는 까닭

| 도구 | 하는 것 | 못 하는 것 |
|---|---|---|
| 전문 공정 도구 (Primavera P6 등) | 계산 | 포인트가 옮겨 간 것을 알려 주지 않음 · 바깥 위험·연락 없음 · 비싸고 배우기 어려움 |
| 엑셀 공정표 | 기록 | CPM·자원 계산이 없음 |
| 범용 AI 챗봇 | 말 | 날짜를 틀림 · 출처가 없음 · 승인 절차가 없음 · 현장 밖 사람에게 닿지 못함 |

### 1-5. 누가 겪나

| 역할 | 겪는 일 |
|---|---|
| 공정 담당 | 변동마다 재계산, 만회 계획 작성 |
| PM | 어디에 힘을 쏟을지 결정, 발주처 보고 |
| 현장 관리자 | 협력사 확인 연락, 현장 보고 |
| 협력사 담당자 | 앱 밖에서 전화·문자로만 소통 |

건설뿐 아니라 생산(설비·금형·납기), 연구개발(시험 장비·인증), 사업화(인허가·계약)도 같은 구조다.

## 2. 해법 — 에이전트의 한 바퀴

### 2-1. 한 바퀴

```
   ┌──────────── ① 변동이 들어온다 ◀───────────────────────────┐
   │   대화 한 줄 · 현장 체크인 · 사진 · 걸려 온 전화·문자 · CSV       │
   ▼                                                             │
 ② 영향을 잰다            코드 — CPM·근무 달력·자원, 오차 0%            │
   ▼                                                             │
 ③ 관리 포인트를 다시 짚는다 코드 — 크리티컬 + 여유 ≤ 3일, 3주 창, 앞 버전과 비교 │
   ▼                                                             │
 ④ 새 포인트의 바깥 위험    Liner — 자재 시세·환율(Premium Data),        │
   ▼                       업체·업종 소식(MCP), 출처 문장(Search Agent)   │
 ⑤ 담당자에게 확인한다      Liner 글 + AI 전화, 연락 하네스              │
   ▼                                                             │
 ⑥ 대안을 견주고 결정한다   「당겨도 소용 있나」(코드) · 만회안 · 승인함(사람) │
   ▼                                                             │
 ⑦ 새 버전 → 관리 포인트 다시 계산 ──────────────────────────────────┘
```

### 2-2. 분업

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **코드** | 날짜·여유·자원·영향·관리 포인트·당김 효과 계산, 4겹 하네스 점검 | 판단 |
| **Liner** | 요청 해석, 작업마다 어떤 바깥 자료를 볼지 고르기, 출처 있는 검색·문장, 연락 글·통화 요약, 만회안 설명, 보고서·차트 | **날짜 계산 · 숫자 지어내기** |
| **사람** | 승인·거부, 조건 확정, 연락 보내기(기본값) | — |
| **연락 하네스** | 시험 모드·근무시간·발송 권한·번호 비공개·통화 근거 대조 | — |

### 2-3. 하지 않는 것 (신뢰의 경계)

| 하지 않음 | 까닭 |
|---|---|
| LLM 이 날짜·여유·자원을 계산하지 않음 | LLM 이 낸 날짜는 코드가 버린다 |
| 바깥 숫자를 일정에 바로 넣지 않음 | 출처·기준 시각과 함께 보여 주고, 넣으려면 조건 미리 보기 → 승인함 |
| 자료가 없을 때 숫자를 만들지 않음 | 「바깥 자료 없음」으로 둔다 |
| 사람 승인 없이 일정을 바꾸지 않음 | 일정 변경은 책임이 큰 결정 |
| AI 가 허락 없이 연락하지 않음 | 모든 문자·전화는 한 함수를 거치고, 기본은 「승인 받기」 |
| 전화번호를 AI 모델에 주지 않음 | 에이전트는 연락처 id·이름·담당만 본다 |
| 통화·문자로 일정을 바꾸지 않음 | 협력사의 변경 요구는 「요청」으로 기록하고 사람이 판단 |

## 3. 솔루션 & 완성도 (30%) — 실제로 도는 한 바퀴

### 3-1. 시연: 같은 3일, 다른 영향

시연 일정 「5층 사무동 신축」(가상). 6월 말 실적과 커튼월·창호 조달 일정이 들어간 **승인된 새 계획**에서 출발한다 — 준공 2027-11-08, 계획 대비 편차 0. 관리 포인트는 5층 거푸집·5층 타설·옥탑 골조(크리티컬)와 4층 거푸집·4층 타설·5층 철근(여유 3일). 아래 숫자는 모두 엔진이 계산한 값이며 자동 시험이 고정한다.

| # | 장면 | 화면 | 결과 |
|---|---|---|---|
| 0 | **약속 만들기** — 말 한 줄 → 질문지 → 생성(코드 계산 → 하네스 위반 → 고침 → 통과) → 승인 | 에이전트 대화 · 질문지 · 승인함 · 간트 · CPM | 〔화면〕 |
| 1 | "창호 제작이 3일 늦어진대" | 대화 · 지연 기록 | 준공 그대로 · 관리 포인트 그대로(창호 줄 여유 18일) |
| 2 | "커튼월 공장 제작도 3일 늦어진대" | 대화 · 지연 기록 · CPM | **준공은 그대로 — 그러나 커튼월 공장 제작·자재 반입·커튼월 설치가 여유 4 → 1 로 새 관리 포인트** |
| 3 | **관리 포인트 카드** 「관리 포인트가 바뀌었습니다」 | 대화 카드 · 주의할 일정 | 새 포인트 3건 + 바깥 위험: 알루미늄 시세·원·달러 환율(Liner Premium Data, 출처·기준 시각) · 커튼월 업종 소식(Liner MCP) · [근거 문장 보기](Liner Search Agent) 〔화면〕 |
| 4 | **담당자 확인** [담당자에게 확인 연락] → AI 전화 | 연락처 | 통화 카드: 받아쓰기·요약·**질문별 답과 근거 발화** · 범위 밖 질문(금액)은 답하지 않고 기록 〔화면〕 |
| 5 | **당겨도 소용 있나** "옥탑 골조를 5일 당기면?" | 대화 카드 · 비교판 | **준공 1일만 당겨짐(11-08 → 11-06) · 다음 결정 줄 = 커튼월 공장 제작 → 자재 반입 → 커튼월 설치** (같은 5일 당김이 커튼월 지연 전에는 4일) → 만회안 B: 준공 11-01(6일), 크레인 1→2대 · 천장 마감 15→12일 · 커튼월 설치 10→8일 → 승인 → 새 버전 → 포인트 다시 계산 |
| 6 | **현장이 먼저 말할 때** 폰 체크인 · 사진 AI 판독 · 걸려 온 협력사 전화 → 「확인할 보고」 → 지연 기록 | 스마트폰 · 연락처 | 현장 계정은 보고만, 결정은 사무실 〔화면〕 |
| 7 | **쌓이는 지식** 월간 보고서(회사 양식 학습, 차트 숫자 전수 대조) · 자료함 · 내 규칙 · 스킬 | 보고서 · 자료함 · 조건·규칙 · 워크플로우 | 〔화면〕 |

> **"같은 공장 제작, 같은 3일. 준공은 둘 다 그대로지만 하나는 약속을 정하는 줄을 옮겼다. 에이전트는 그것을 알아보고, 그곳에 무엇이 다가오는지 찾아, 담당자에게 먼저 묻는다 — 그리고 엉뚱한 곳을 당기려 하면 소용이 없다고 말해 준다."**

### 3-2. 일정 OS — 앱 18개, 기기 셋

| 묶음 | 앱 |
|---|---|
| 시스템 | 에이전트 대화 · 질문지 · 워크플로우 · 승인함 · 탐색기 · 설정 · 개발 콘솔(관리자) |
| 일정 | 스케줄 · 간트차트 · CPM · 공정률(+ 현장 점검) · 비교판 · 조건·규칙 · 지연 기록 · 보고서 |
| 연결 | 프로젝트 관리 · 연락처(문자·AI 전화) · 자료함 |

- **태블릿**: 좌우 분할. **스마트폰**: 아래 탭 5개, 현장 계정은 현장 점검·일정·현장 AI.
- 계정 3등급(관리자·사용자·현장 관리자) · 회원가입 승인 · 프로젝트별 자료 격리 · 열어 둔 창을 기기 사이에 이어서.

## 6. 확장성과 임팩트 (20%)

### 6-1. 본질이 같으니 산업만 바뀐다
- 같은 엔진, 같은 한 바퀴. 분야마다 달라지는 것은 **어떤 바깥 자료를 볼지** 뿐이다(설정에서 켜고 끔).

  | 분야 | 날씨 | 금속·원자재 | 환율 | 업종·업체 |
  |---|---|---|---|---|
  | 건설 | ● | ● | ● | ● |
  | 생산 | — | ● | ● | ● |
  | 그 밖(연구개발·사업화 등) | — | — | — | ● |

- 생산 일정 「브래킷 BR-200 2만 개」(가상): 설비 자원별 간트, 「프레스 작업 금지」 띠, 납기선 — 같은 엔진으로 처리. 〔화면〕
- 처음 보는 산업은 분야 팩(용어·WBS 계층·위험 규칙)을 즉석에서 합성한다.

### 6-2. 앱 밖의 사람까지
- 협력사 담당자는 앱을 깔지 않아도 문자·AI 전화로 한 바퀴에 들어온다. 걸려 온 전화도 에이전트가 받아 보고로 남긴다.
- 여러 언어 통화 — 외국인 작업자·해외 현장.

### 6-3. 임팩트
- **헛수고를 막는다**: 시연에서 같은 「골조 5일 당김」의 값어치가 4일에서 1일로 바뀌는 것을, 힘을 쏟기 **전에** 코드가 알려 준다.
- **늦게 아는 시간을 없앤다**: 주간 회의에서야 알던 포인트 이동을 변동이 들어온 그 순간에 안다. 변동 보고부터 담당자 확인 통화까지 〔실측: 시연 녹화 시간〕.
- **확인이 기록으로 남는다**: 통화의 질문별 답과 근거 발화가 일정 옆에 남아, 다시 묻지 않는다.
- **회사마다 쌓인다**: 보고서 양식 학습, 내 규칙, 스킬, 자료함.

## 부록 A. 기술 구조 (개발자 심사용)

- **결정론적 일정 엔진** `backend/app/core/`
  - `calendar.py` 근무일 서수 배열 + 이분 탐색으로 공휴일·금지 기간을 반영한 날짜 연산.
  - `cpm.py` 위상 정렬로 순환을 막고 FS/SS/FF/SF + lag, SNET/FNLT, Data Date 기준 전진·후진 패스로 ES/EF/LS/LF·TF/FF.
  - `resources.py` (ES, TF, id) 우선순위로 일일 용량을 넘지 않는 시작 자리를 찾아 후행으로 전파.
  - `shorten.py` 병행·압축·자원 추가를 한 수씩 넣고 다시 계산하며, 옮겨 가는 크리티컬 패스를 추적해 만회안 묶음을 만든다.
  - `delay.py` 지연 전후 크리티컬을 비교해 새로 크리티컬이 된 작업·빠진 작업·새 자원 겹침을 낸다.
  - `points.py` 관리 포인트(크리티컬 + 여유 ≤ k, w 주 창)와 버전 사이 차이 · `accel.py` 당김 효과(당긴 일수 대비 준공 반영, 다음 결정 줄). 〔갱신: 계획 5 최종 이름〕
- **4겹 하네스** `backend/app/harness/` — 기본 < 분야 < 내 규칙 < 입력 우선순위로 경합 판정, 자동 점검 안 되는 조건은 따로 표시.
- **에이전트** `backend/app/agent/` — ReAct 루프(단계 한도 설정), 도구 실행 전 커밋·실패 시 되돌림, 자가 점검, 화면·요청에 맞춘 지침 선택, 스킬 매칭. 도구 40여 개.
- **연락** `backend/app/outreach/`·`notify/` — 나가는 문(시험 모드 → 차단 → 근무시간 → 상한 → 권한 → 중복), 들어오는 문(번호로 등급), 통화 하네스(코드가 정한 첫마디, 도구 범위, 받아쓰기와 도구 결과 대조).
- **화면** `frontend/src/os/`·`programs/` — React OS 셸, 앱 18개, PC·태블릿·폰 셸.
