## 1. 무엇을, 왜

**[PM]** 기존 스케줄 에이전트를 이어 쓰지 않고, 새로운 형태의 스케줄 에이전트를 대회 기간에 새로 만든다. 신청 때와 방향은 같다(스케줄 에이전트) — 주최 측에 따로 알리지 않는다.

- 화면은 기개발한 프로젝트 플랫폼 OS(미니PC `~/project-platform`)와 같은 **OS 형태**로, 코드를 가져오지 않고 새로 만든다.
- OS 전체를 맡는 에이전트(LLM·루프·컨텍스트·ReAct·하네스·워크플로우)가 하나 살아 있다.
- 일생 순서를 프로그램에 심지 않는다. **에이전트가 워크플로우를 만들어 도구를 쓴다.**
- 대상 분야: 제조·생산, 건설, 연구개발, 사업화.
- **AI만 쓰는 도구는 뒷단에, 사용자가 같이 보거나 고칠 것은 OS 프로그램으로.**
- 일정 생성은 에이전트 대화창에서 프롬프트로. 에이전트가 조건을 묻고, 모자란 것을 더 묻고, 생성한다. 입력 조건이 그 일정의 하네스가 되어 기존 하네스와 합쳐진다.
- 생성물은 완성본: WBS → 스케줄 → 간트 → 크리티컬 패스.
- 질문의 자세한 정도는 사용 목적·정확도에 따라 조절(5단계).

**[제안] 왜 이 형태인가** — 대회 주제 "노하우를 실행하는 에이전트". 내 규칙·스킬(저장된 워크플로우)·보고서 양식이 쌓일수록 그 사람의 방식으로 일정을 만들고 고친다. 전부 대회 기간 신규라 제4조 2항 구분 부담이 없다.

## 2. 목표 / 하지 않는 것 / 실패로 보는 것

**목표**
1. 대화로 네 분야의 일정 완성본을 만든다.
2. 변화(지연·조건 변경·자원 변경)를 말하거나 조건을 바꾸면 영향이 계산되고 대안이 나온다.
3. 에이전트가 일하는 과정(조건, 생성 회차, 워크플로우, 에이전트 구조)이 화면에 보인다.
4. Liner Model API = 에이전트 두뇌, Liner Search = 근거 검색. 둘 다 핵심 기능(제4조 1항).
5. 5분 데모 영상으로 찍을 수 있는 안정성.

**하지 않는 것**
- 비용·예산 관리 (지연 기록의 "일수 × 하루 금액" 환산만) **[PM]**
- P6 XER·MS Project 파일, 한글(hwp) 문서
- 작업마다 자원을 입력하는 화면, 전체 자원 배정 **[PM]**
- "예정(Forecast)" 날짜 칸 **[PM]**
- 승인 권한을 등급으로 나누기 **[PM]**
- 정해진 시각에 스스로 도는 점검, 사용자가 워크플로우 단계를 직접 편집
- 모바일·좁은 화면 (FHD 1920×1080 기준), 키 없이 도는 시연 모드
- 기존 `~/schedule-management`·`~/project-platform` 코드 복사, 디자인 시스템 패키지 사용

**실패로 보는 것**
- LLM이 날짜를 계산하는 것 (계산은 항상 코드)
- 점검하지 않은 조건을 점검한 것처럼 보이는 것
- 회사 실제 자료·개인정보가 예시에 들어가는 것 (제5조)
- API 키가 저장소에 들어가는 것 (제4조 6항)
- 많은 기능을 얕게 만들어 시연에서 끝까지 도는 것이 없는 것

| | 방법 | 판단 |

```
┌ OS 화면 (브라우저) ─────────────────────────────────────────┐
│ 로그인 · 메뉴바 · 바탕화면(위젯) · 창 관리 · Dock              │
│ 시스템: 대화창 / 질문지 / 워크플로우·스킬 / 승인함 / 탐색기 / │
│         알림 / 설정 / 개발 콘솔(관리자)                       │
│ 업무:   일정판 / 비교판 / 조건·규칙 / 지연 기록 / 보고서       │
└───────────────┬────────────────────────────────────────────┘
                │ REST + SSE
┌ 서버 ─────────▼────────────────────────────────────────────┐
│ OS 에이전트: 루프(ReAct) · 컨텍스트 조립 · 워크플로우 실행기   │
│ 하네스 네 겹 → 조건 점검        승인 판단 · 버전 · 변경 이력   │
│ 도구 등록부 + 뒷단 도구(계산 코드)   분야 묶음 4개             │

└───────────────┬────────────────────────────────────────────┘
        Liner Model API (두뇌) · Liner Search API/MCP (근거)
```

**[제안] 기술**: 화면 React + TypeScript + Vite, 서버 Python FastAPI, SQLite. Liner Model API는 OpenAI SDK에 base_url 교체(`../01_대회정보/API문서/`). `docker compose up` 으로 실행.
**[제안] 위치**: 맥 `~/projects/chronos` (새 git 저장소, 브랜치 작업). 포트 서버 8200·화면 5600.

## 8. 일정판

**[PM]** 기존 스케줄 에이전트(`~/schedule-management`)의 스케줄표·간트·CPM 화면과 **같은 기능·같은 형태**로 만든다. 코드는 가져오지 않고 새로 쓴다(형태 참고: `~/schedule-management/frontend/e2e/screens/스케줄-1920.png`, `간트-1920.png`, `CPM-1920.png`). 달라지는 것은 둘 — Forecast 없이 Plan/Actual 두 벌, 웹 페이지가 아니라 OS 창 안.

탭 넷: **스케줄표 / 간트 / CPM / 진행**. 간트 하나로 네 분야를 본다 [PM: 간트 선호]. 용어는 기존 것을 쓴다(액티비티, OD·RD, TF·FF, Data Date).

### 8-1. 스케줄표
| 칸 | 내용 | 고침 |
|---|---|---|
| ID | WBS 묶음 줄(접기/펴기)과 액티비티 ID | 자동 |
| 이름 | | ● |
| 유형 | 작업 / 시작 마일스톤 / 종료 마일스톤 | ● |
| WBS | 속한 WBS | ● |
| 가중치(%) | 공정률 계산용. 가중치 방식(기간 비례 기본 / 직접 입력) | 방식에 따라 |
| OD · RD | 원래 기간 · 남은 기간(근무일) | ● |
| **Plan 시작·종료** | 처음 생성한 일정. 코드가 계산 | OD·선행·제약을 고치면 바뀜 |
| **Actual 시작·종료** | 실적. Plan보다 빠르든 늦든 실제 날짜 | ● |
| 진도(%) | 실적 % | ● |
| 상태 | 계획 내 / 지연 +n일 / 선행 −n일 / 완료 / 조건 위반 | 자동 |
| TF · FF | 전체 여유 · 자유 여유 (TF 0 = 크리티컬) | 계산 |

- 켜는 칸: 제약, ES/EF·LS/LF, 불확실 기간(낙관·보통·비관), 납기, 주요 자원(읽기 전용), 담당, 메모. 분야에 따라 기본으로 켜지는 칸이 다르다.
- 위 도구줄: 행 추가·삭제, 검색, 필터, 열 고르기, 되돌리기·다시 하기, 가중치 방식, CSV 내보내기·가져오기. 머리줄에 Data Date, 완료 예정, 크리티컬 수, 음수 여유 수, 경고 수.
- 아래 **관계 패널**: 고른 액티비티의 선행·후행을 종류(FS·SS·FF·SF)와 간격으로 편집. 표의 선행 칸(`A1020 SS+15`)으로도 입력.
- **Plan / Actual [PM]**: 예정(Forecast) 칸 없음. 지연·선행은 Plan과 Actual의 차이에서 계산. 아직 안 한 액티비티가 얼마나 밀리는지는 칸이 아니라 **지연 영향 분석 결과**(간트의 흐린 막대, 지연 기록, 비교판)로 본다. 만회 계획 승인 등으로 일정을 다시 잡으면 Plan이 새 버전이 되고 처음 Plan은 버전에 남는다 [제안].
- **Data Date**: 실적의 기준일. 실적 입력·공정률·지연 판정이 이 날짜 기준.

### 8-2. 간트
- 왼쪽 WBS/ID 나무 + 표(이름·OD·RD…, 열 고르기), 오른쪽 월·주 날짜 머리와 막대, 가운데 나눔선.
- 위 도구줄: 층 단추 **Plan · Actual · CPM**(켜고 끔), 확대·축소, 맞춤·선택 맞춤, Data Date, 오늘, 앞뒤 이동, 모두 펼치기·접기, 열, 범례, 되돌리기·다시 하기, CSV·그림 내보내기.
- CPM 층: 크리티컬 빨강, 여유, 관계선. Plan만 켜도 CPM 층이 보인다.
- **묶는 기준**(추가): WBS(기본) / 자원(주요 자원별 줄 — 생산의 설비별 보기) / 일정(여러 일정 요약 + 일정 사이 연결).
- 그 밖의 겹쳐 보는 표시: 진도 채움, 지연 흐린 막대, 조건 위반 표시, 승인 전 변경안(점선), 불확실 범위선, "늦어도 시작" 눈금, 납기·관문·출시 ◆.
- 아래에 주요 자원 부하 막대.
- 직접 고치기: 표 수정, 막대 끌기, 액티비티 추가·삭제. 고치면 바로 재계산·조건 점검.
- 달력: 주 5/6일, 교대, 한국 공휴일, 작업 금지 기간.

### 8-3. CPM
- 액티비티를 카드로 그린 네트워크 다이어그램. 카드: ID, 상태, 이름, Plan 대비 차이, ES/EF, LS/LF, OD/RD, TF/진도, Plan 날짜. 마일스톤은 ◇ 카드. 카드 사이 관계 화살표(FS 등 표시).
- 위 도구줄: 층 단추, 보기(전체 / 크리티컬 경로만 / 선택 항목), 검색·찾기, 자동 배치, 맞춤, WBS 필터, 범례, PNG 내보내기. 확대·축소·화면 맞춤.
- 요약 줄: Plan 준수율, 크리티컬 경로 총 변동, 만회 계획 달성률, 프로젝트 완료 편차.
- 오른쪽 패널: 상세(고른 카드의 날짜·여유·선후행, 화살표를 누르면 관계 편집) / 변동 분석.

### 8-4. 진행 [PM]
계획 공정률 대 실적 공정률(전체·WBS 묶음별, 가중치 사용), S-커브(계획·실적 누적선, Data Date 기준 차이). 보고서에 자동으로 들어간다.

### 8-5. 실적 입력
대화("골조 60% 됐어") 또는 스케줄표. 입력하면 재계산하고, 지연이 감지되면 에이전트가 지연 기록 등록과 대응을 제안한다.

## 9. 조건·규칙 (하네스)

### 9-1. 네 겹
| 겹 | 예 | 성격 |
|---|---|---|
| 기본 규칙 | 선후 고리 없음, 떠 있는 작업 없음, 달력 준수 | 항상. 못 바꿈 |
| 분야 규칙 | 건설: 타설 뒤 양생 / 생산: 설비 용량 / 연구개발: 관문 앞 검토 / 사업화: 인증 뒤 출시 | 분야 묶음. 관리자만 수정 |
| 내 규칙 | "층당 골조 10일", "타설 다음 날 그 층 작업 없음", "보고서는 월요일 기준" | 에이전트가 제안 → 사용자 확인 뒤 저장. 범위는 분야 전체 또는 이 일정 |
| 입력 조건 | 준공 11.30 이전, 12~2월 타설 금지, 크레인 1대 | 대화에서 뽑음 |

- 뒤 겹이 앞 겹과 부딪히면 뒤 겹을 따르고 표시. 기본 규칙은 예외.
- 조건은 일정에 붙어 저장되고, 이후 모든 변경이 같은 조건으로 점검된다.
- 코드로 점검되는 조건과 말로만 되는 조건("안전 우선")을 나눈다. 뒤쪽은 "자동 점검 안 됨" 표시.

### 9-2. 자원 조건 [PM]
작업마다 설정하지 않는다. 일정의 **주요 자원**만 조건·규칙 창에 줄로 올린다: 자원 · 수량 · 가장 몰리는 때(필요 수량) · 쓰는 작업 수.
- 주요 자원은 생성할 때 에이전트가 분야와 대화에서 골라 올리고, 작업과의 연결도 에이전트가 작업 유형을 보고 붙인다.
- 확인·수정은 자원 쪽에서("쓰는 작업 ▸" 목록에서 빼고 더함) 또는 대화로.
- 투입을 늘려 기간을 줄이는 것은 에이전트의 단축안으로 다룬다(승인하면 수량과 기간이 같이 바뀜).

### 9-3. 조건을 바꾸면 실시간으로 [PM]
- 계산만으로 되는 변경(기한, 달력, 자원 수량, 기간 기준): 코드가 즉시 재계산, 간트가 움직이고 이전 위치는 흐린 막대.
- 구조를 바꿔야 맞는 변경(위반 발생): 위반 표시 + "에이전트에게 맞추게 하기" → 생성 루프.
- 바꿔 보는 동안은 미리 보기. "확정"을 눌러야 반영(승인 기준 10-3).

## 10. 에이전트

### 10-1. 루프
요청 → 컨텍스트 조립(지시문·분야 묶음·하네스·스킬 목록·내 규칙·화면 맥락·대화) → 맞는 스킬이 있으면 스킬 실행, 없으면 워크플로우 짜기 → 판단·도구 실행·결과 관찰 반복 → 조건 점검(위반이면 고쳐 다시) → 승인 판단 → 응답·기록.
- 에이전트는 등록된 도구만 쓴다. 입력 형식이 틀리면 실행 전에 걸러 돌려준다. 단계 수·다시 짜기에 한도.
- **창 열기** 도구로 결과를 해당 프로그램에 띄운다(워크플로우가 도는 동안 창이 열리며 채워진다).

### 10-2. 워크플로우와 스킬 [PM: 저장 + 스킬 등록, 너무 많아지지 않게]
| 단계 | 생기는 법 | 에이전트가 쓰나 |
|---|---|---|
| 실행 기록 | 전부 자동 | 아니오 |
| 저장 | 사용자가 골라 이름 붙임 | 아니오(사용자가 다시 실행) |
| 스킬 | 저장한 것 중 직접 등록. "언제 쓰는지" 설명 + 바뀌는 값(빈칸) | 예 — 요청이 오면 먼저 찾음 |

- 다시 실행·스킬 실행은 순서 고정, 빈칸 값만 에이전트가 사용자 말에서 채운다.
- 에이전트는 비슷한 워크플로우가 세 번 반복되면 등록을 **제안만** 한다. 등록 때 비슷한 스킬이 있으면 고칠지 묻는다. 스킬마다 실행 횟수·마지막 사용일. 에이전트에는 이름과 한 줄 설명만 먼저 보인다.

### 10-3. 승인 기준 [PM: 전부 승인은 과함. 되돌리기 전제로 중요한 것만]
| 자동 적용(알림 + 되돌리기) | 승인 필요 |
|---|---|
| 실적 입력에 따른 재계산 | 끝 날짜·주요 마일스톤·납기·관문일이 바뀜 |
| 여유 안에서 흡수되는 날짜 변경 | 크리티컬 패스가 바뀜 |
| 조건을 모두 통과하는 순서·자원 조정 | 조건 위반 또는 조건 자체를 바꿈 |
| 보고서·만약에 복사본 만들기 | 작업·관계 삭제, WBS 구조 변경 |
| | Plan을 다시 잡음, 영향이 다른 일정으로 넘어감 |
| | 새로 만든 일정의 첫 저장, 내 규칙 저장 |

되돌리기는 묶음 단위(에이전트가 한 번에 바꾼 것을 버튼 하나로). 관리자가 수준을 고른다: 전부 승인 / **중요한 것만(기본)** / 전부 자동. 승인·거부는 모든 계정이 한다.

## 11. 일정 생성 (대화 + 질문지)

### 11-1. 흐름
1. 대화창에 프롬프트로 요청 → 분야를 읽는다(애매하면 묻는다).
2. 사용 목적을 확인해 정밀도를 정한다(읽히면 묻지 않는다).
3. 에이전트가 채울 수 있는 것을 먼저 채운다 — 프롬프트, 올린 문서, 내 규칙, 분야 기본값.
4. 필수 정보 중 빈 것을 질문 목록으로 만들어 **질문지** 프로그램을 연다(11-4). 사용자가 고르거나 직접 입력한다.
5. 제출하면 생성 루프(11-5). 대화 안 생성 과정 카드에 단계와 회차별 위반 수.
6. 일정판에 열고, 첫 저장은 승인 뒤. "가정한 것"을 밝힌다.
7. 이후 대화나 일정판에서 고친다 — 같은 조건으로 점검.

### 11-2. 정밀도 5단계 [PM]
| 단계 | 쓰는 곳 | WBS 깊이 | 액티비티 수 | 단위 | 꼭 받는 정보 | 생략 가능 | 자원 |
|---|---|---|---|---|---|---|---|
| L1 마스터 | 경영 보고·제안 | 1~2 | 10~20 | 월 | 5~6개 | 4개 | 없음 |
| L2 요약 | 타당성·계약 | 2~3 | 20~40 | 주 | 10~12개 | 5개 | 없음 |
| L3 관리 | 계획 수립·월간 보고 | 3 | 50~100 | 일 | 18~22개 | 6개 | 주요 자원 |
| L4 실행 | 주간 관리 | 4 | 100~200 | 일 | 30개 안팎 | 적음 | 주요 자원 |
| L5 상세 | 3주 앞 작업 계획·작업 지시 | 5 | 고른 구간만 | 일·교대 | L4 전부 + 구간 10개 안팎 | 적음 | 주요 자원 |

(항목 수는 분야 고유 항목 포함. PM 지적으로 앞 판의 3·5·8·12·15개에서 올림.)

- L5는 기간·구간을 정해 그 부분만.
- **더 자세히 풀기**: 상위 단계 일정의 한 묶음을 골라 아래 단계로 푼다. 상위 날짜는 조건으로 고정.
- L4 이상은 WBS를 먼저 보여 확인받고 진행. L3 이상은 생성 중 Liner Search를 최대 3번 써 분야 기준 기간을 찾고 가정에 출처를 붙인다(실패하면 기본값 + 표시).

### 11-4. 질문지 프로그램 [PM]
에이전트가 사용자에게 물을 것이 **세 개 이상**이면 질문 목록을 만들어 이 프로그램을 연다(한두 개면 대화 안의 작은 카드).

- 위: "필수 n개 중 m개 채움" 진행 막대, 묶음 탭(범위 / 날짜 / 달력·방식 / 자원·외부).
- 이미 채운 항목: 값 + 출처(프롬프트·문서·내 규칙·분야 기본값) + [고치기].
- 남은 질문: 에이전트가 만든 선택지 2~4개(권할 것에 추천 표시) + **직접 입력**. 생략 가능 항목에만 "알아서".
- 답에 따라 질문이 생기고 사라진다("지하 1층" → "흙막이 방식은?").
- 아래: [나머지는 알아서](생략 가능 항목만) · [대화로 답하기] · [제출하고 생성]. 필수가 다 채워져야 제출된다.
- 질문지를 연 채 대화창에 답을 쓰면 해당 칸이 채워진다.
- 답은 그 일정의 조건(하네스)이 되고, 조건·규칙 창에 출처 "질문지"로 남는다. 생략한 것은 "가정한 것"에 남는다.
- 생성 말고도 쓴다: 지연 사건 등록(원인·책임·하루 금액), 보고서 양식 등록(항목별 자료 연결), 만회 계획(허용하는 방법), 문서에서 변화 뽑기(애매한 내용 확인).

### 11-5. 생성 단계
① WBS → 점검(빠짐·겹침·깊이) ② 스케줄(OD·선후·달력·주요 자원 연결) → 점검 ③ 코드 계산 → 간트 ④ 크리티컬 패스·여유 ⑤ 조건 점검(네 겹) → 위반이면 해당 단계로 돌아가 고치고 ③부터.
①②는 LLM 초안, ③④⑤는 코드. 한도까지 못 맞추면 가장 나은 안 + 부딪히는 조건을 보고.

## 12. 개발 콘솔 (관리자) [PM]

| 탭 | 내용 |
|---|---|

### 12-1. LLM 연결과 작업별 모델 배정 [PM]

Liner는 키 하나·주소 하나로 요청마다 `model` 값만 바꿔 쓸 수 있다(`../01_대회정보/API문서/liner-model-api.md`). 연결을 여러 개 만들지 않는다.

- **LLM 연결(설정, 관리자) [PM: 플랫폼 OS의 LLM 연결과 같은 구성]** — 형태 참고: 미니PC `~/project-platform/src/system-apps/settings/llm/`(코드는 새로 씀).
  - 연결 목록: 카드마다 이름·공급자 배지·상태 배지(연결됨 · 모델 n개 / 연결 실패 / 미확인)·마지막 확인 시각·[연결 테스트]·[URL 수정]·[키 교체]·[삭제].
  - 연결 추가 마법사 3단계: ① 공급자 고르기(**Liner — 기본**, 주소 `https://platform.liner.com/api/v1` 미리 채움 / 직접 URL(OpenAI 호환)) ② 이름·URL·API 키 입력 ③ 연결 테스트 → 응답 시간과 모델 목록(`GET /v1/models`) 표시 → 저장.
  - 키는 서버에서 암호화 저장하고 화면에는 끝 4자리만. 주소를 다른 호스트로 바꾸면 키를 다시 넣어야 한다. 오류는 원인별 문구(키 틀림·주소 틀림·시간 초과·한도 초과).
  - 연결이 없으면 대화창에 "LLM 연결이 필요합니다 → 설정 열기" 안내.
  - **키는 PM이 직접 입력한다**: 서버를 테일넷 주소로 띄우고(0.0.0.0 바인딩), PM이 브라우저에서 넣는다. Claude는 키를 받거나 파일에 쓰지 않는다. 근거 검색도 같은 키.
- **작업별 모델 배정 표**: 에이전트가 하는 일의 종류마다 모델 또는 라우터(+ `routing_strategy`: cost / balanced / quality)를 고른다.

| 에이전트가 하는 일 | 기본 배정 [제안] | 이유 |
|---|---|---|
| 조건 뽑기, 분야 읽기, 문서에서 변화 뽑기 | 라우터 `cost` | 단순하고 자주 일어남 |
| 대화, 워크플로우 짜기, 보고서 초안 | 라우터 `balanced` | 중간 |
| WBS·스케줄 생성, 단축안, 위반 고치기 | 라우터 `quality` | 판단이 어렵고 결과에 영향이 큼 |
| 긴 문서 통째로 읽기 | `liner-mark` | 컨텍스트 105만 토큰 |

- 라우터: `liner-gpt-router`, `liner-claude-router`, `liner-gemini-router`. 어느 계열을 기본으로 할지는 첫날 시험 뒤 정한다.
- 응답의 실제 모델 이름과 `usage.cost` 를 기록해 개발 콘솔(실행 추적·사용량·비용)에 보여 준다 — 작업별로 모델이 달라지는 것과 비용 차이가 보인다.
- **첫날 확인**: 모델·라우터별 도구 호출, 정해진 형식 답, 그림 읽기, 호출 한도. 결과로 배정 표를 확정한다. 어느 쪽이든 Liner Model API 안에서만 고른다(다른 회사 API 직접 호출 없음).

## 18-1. 진행 방식과 코드 규정 [PM 승인 11-19]

**진행**: 순서대로(한 번에 한 작업, 끝나면 확인 뒤 다음). 작업 난이도별 모델 — 고도화 **fable**(에이전트 루프·하네스·워크플로우, 일정 계산, 간트·CPM 그리기, 화면 디자인, 검토) / 일반 **opus**(명세가 분명한 프로그램 화면·API, 뒷단 도구, 시험) / 단순 **sonnet**(예시·분야 자료, 반복 수정, 형식 변환). 계획서의 작업마다 등급을 적는다.

**화면 시안**: 구현 전에 프로그램별로 전부(로그인, OS 화면, 프로그램 13개, 설정 메뉴 구성 포함). OS 화면·일정판은 기존 형태라 한 가지, 배치에 선택의 여지가 있는 화면은 두 가지 안.

**모듈 구조**: 프로그램·기능 단위 폴더.
```
화면  src/os/  src/programs/<이름>/  src/shared/
서버  app/programs/<이름>/  app/tools/<묶음>/(도구 하나 = 파일 하나)
      app/agent/  app/core/(순수 계산)  app/domains/<분야>/(자료 파일)
```
- 프로그램끼리 직접 불러 쓰지 않는다(공통 서비스·이벤트로만).
- 뒷단 도구는 등록부에 올리고 에이전트는 등록부만 본다.
- core 는 LLM도 저장소도 모른다. 분야 묶음은 코드가 아니라 자료.
- 모듈이 밖에 내놓는 것은 입구 파일 하나. 모듈마다 짧은 설명 파일과 시험을 같은 폴더에.

**파일 길이**: 기준은 "파일 하나에 일 한 가지". 줄 수는 그것을 어겼는지 알려 주는 신호.
| 대상 | 권장(넘으면 경고) | 상한(넘으면 커밋 막힘) |
|---|---|---|
| 화면 파일 | 300줄 | 600줄 |
| 서버 파일 | 400줄 | 800줄 |
| 함수 | 50줄 | 100줄 |
시험·자동 생성·자료 파일은 제외. 상한 예외는 이유를 적어 예외 목록에. 줄 수와 모듈 경계 위반은 커밋 전 자동 검사.
