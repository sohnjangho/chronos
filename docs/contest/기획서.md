## 한 줄

**일정을 만들고, 지키고, 고치는 에이전트 OS.** 대화 한 줄로 공정표를 만들고, 조건이 바뀌면 코드가 다시 계산하고, 바꾸는 결정은 사람이 승인한다.

## 1. 문제 정의

### 1-1. 누가 불편한가

건설·플랜트·생산 프로젝트에서 공정표를 관리하는 사람이다.

| 역할 | 하는 일 |
|---|---|
| 공정 담당 | 주 1회 진도 갱신, 만회 계획 작성 |
| PM | 지연 원인 파악, 발주처 보고 |
| 현장소장 | 3주 룩어헤드 확인, 자재·인력 투입 계획 |

### 1-2. 무엇이 병목인가

**공정표는 만들 때보다 고칠 때 시간이 든다.**

| 상황 | 걸리는 시간 |
|---|---|
| 진도 5% 밀렸을 때 만회 계획 세우기 | 반나절 |
| 발주처 요구로 마일스톤 3개 앞당기기 | 하루 |
| 다른 도구의 공정표를 받아 엑셀로 옮겨 검토 | 2~3시간 |
| 회의록에서 변경사항을 뽑아 공정표에 반영 | 매주 2시간 |

| # | 문제 |
|---|---|
| 1 | **도구가 무겁다.** 전문 공정 도구는 배우기 어렵고, 엑셀은 계산을 못 한다 |
| 2 | **AI 를 붙이기 어렵다.** 공정표는 구조가 복잡해 LLM 에 통째로 넣으면 날짜가 깨진다 |
| 3 | **검증이 안 된다.** AI 가 만든 일정이 맞는지 사람이 처음부터 다시 확인해야 한다 |

### 1-3. 왜 지금인가

LLM 이 도구를 부르고(도구 호출), 정해진 모양으로 답하고(JSON 스키마), 100만 토큰을 읽는다(`liner-mark`). 계산은 코드에 맡기고 판단과 설명만 LLM 에 맡기는 구조를 이제 만들 수 있다. 기존 공정 도구는 이 구조로 되어 있지 않다.

## 2. 솔루션

### 2-1. 형태를 새로 잡은 이유

신청 때의 방향(공정표를 읽고 고치는 스케줄 에이전트)은 그대로다. 형태는 대회 기간에 처음부터 새로 잡았다.

| 신청 때 생각 | 새로 잡은 형태 | 까닭 |
|---|---|---|
| 기존 공정 화면에 AI 기능을 덧붙임 | **OS 형태** — 에이전트 하나가 전체를 맡고, 사람이 보고 고칠 것만 창(프로그램)으로 | 대회 주제 "노하우를 실행하는 에이전트". 프로그램에 순서를 심지 않고 에이전트가 워크플로우를 짜서 도구를 쓴다 |
| 고칠 때 AI 에게 묻기 | **조건(하네스 네 겹)을 바꾸면 바로 다시 계산** | 병목이 "고칠 때"다. 기본 규칙 · 분야 규칙 · 내 규칙 · 입력 조건을 한 곳에서 보고 바꾼다 |
| 정해진 질문 목록 | **질문지를 에이전트가 그 자리에서 만든다** | 분야·정밀도마다 모자란 것이 다르다. 답하지 않은 질문은 적힌 가정으로 넘어가고 「가정한 것」으로 남는다 |
| 기존 코드 위에 신규 일부 | **저장소 전체가 대회 기간 신규** | 기존/신규 구분(제4조 2항) 부담이 없다 |
| 공정 파일 변환 중심 | P6 XER·MS Project 파일은 이번 범위에서 뺌. 엑셀 공정표는 대화에 붙여 일정 초안으로 가져오기(계획 3, 설계) | 대화 → 생성 → 고침의 한 흐름을 끝까지 돌게 하는 데 집중 |

### 2-2. 원칙

| 원칙 | 구현 |
|---|---|
| **계산은 코드, 판단·설명은 LLM** | LLM 은 WBS·기간·선후 관계만 낸다. 날짜·여유·자원 겹침·조건 통과는 `app/core`·`app/harness` 가 계산한다. LLM 이 보낸 날짜는 버린다 |
| **점검하지 않은 것을 통과로 보이지 않는다** | 자동 점검이 안 되는 조건은 「자동 점검 안 됨」으로만 보인다 |
| **AI 는 제안, 사람은 승인** | 첫 저장·준공·마일스톤·크리티컬 패스·조건이 바뀌면 승인함으로. 여유 안에서 흡수되는 변경은 바로 반영(되돌릴 수 있음) |
| **모든 변경은 버전** | 버전·변경 이력·되돌리기. 「처음 계획」 표시 |

### 2-3. 흐름

```
대화 "5층 사무동 공정표 만들어 줘…"
  → 에이전트가 질문지를 만들어 묻는다(답 안 하면 가정)
  → 생성: WBS → 액티비티 초안 → 코드가 날짜·크리티컬 계산 → 조건 점검 → 어기면 LLM 이 고침(최대 5회)
  → 승인함 → 승인 → 버전 1
  → 간트차트·CPM·공정률에서 본다 → 조건·규칙에서 바꿔 미리 보기 → 확정 → 승인 → 새 버전
  → 지연이 생기면 기록 → 영향 분석 → 만회안 → 비교판 → 승인
```

## 4. Liner API 활용

| Liner | 쓰는 곳 | 코드 |
|---|---|---|
| **Model API** — 에이전트 두뇌 | 대화 루프의 도구 호출, 일정 생성(WBS·초안·고침, JSON 스키마), 조건 뽑기, 단축안 설명 | `backend/app/llm/client.py` |
| **라우터 · 작업별 배정** | 쓰임새 넷에 모델·전략을 나눠 둔다: light=`liner-claude-router`·cost(조건 뽑기) · normal=balanced(대화) · hard=quality(생성) · longdoc=`liner-mark`(긴 문서). 화면 「설정 > LLM 연결」에서 바꾼다 | `backend/app/llm/assignments.py`, `backend/app/programs/llm_settings/` |
| **Search API** | 근거 검색(web·scholar) — 조건의 출처 링크로 남긴다 | `backend/app/llm/search.py` |
| **MCP 분야 검색** | `search_legal`(인허가·법정 기간) · `search_business`(공급업체·납기). 기본값이 없는 항목은 지어내지 않고 묻는다 | `backend/app/llm/mcp_client.py` |

실측(`docs/dev-journal/2026-11.md`): Model API 22번 모두 200 — 도구 호출(작은 도구·실제 도구 9개), JSON 스키마 응답, 라우팅 전략별 답한 모델, 그림 입력. MCP 5번 모두 성공(initialize·tools/list·tools/call 200, notifications/initialized 202) — 법령·기업 검색. 응답의 `model` 칸에는 실제로 답한 모델이 오고, 그대로 사용량 기록에 남는다.

## 5. 확장성과 임팩트

### 5-1. 시간

| 작업 | 지금 | ChronOS |
|---|---|---|
| 만회 계획 | 반나절 | **[확인]** 시연에서 잰 시간 |
| 조건(자원·기한) 바꿔 보기 | 다시 짜기 | 값 하나 바꾸면 바로 미리 보기 |
| 새 공정표 초안 | 며칠 | 대화와 질문지로 몇 분 **[확인]** |

### 5-2. 넓히기

| 방향 | 방법 |
|---|---|
| 분야 | 분야 묶음(YAML) 하나를 더하면 된다 — 건설·생산 다음 연구개발·사업화 |
| 사람의 방식 | 내 규칙이 쌓일수록 그 사람의 방식으로 만들고 고친다(워크플로우를 스킬로 저장해 다시 쓰기는 설계) |
| 조직 | 승인 수준(전부·중요한 것만·위반만)으로 팀의 결재 방식에 맞춘다 |
| 모델 | 작업별 배정이라 더 싸거나 더 좋은 모델이 나오면 화면에서 바꾼다 |

### 5-3. 다른 것과

| 기존 | ChronOS |
|---|---|
| 전문 공정 도구 | 배우기 어렵고 AI 가 없다 → 대화와 질문지로 시작 |
| 엑셀 공정표 | 계산·CPM 이 없다 → 코드가 계산 |
| 범용 챗봇에 공정표 질문 | 날짜 계산이 틀리고 검증할 수 없다 → 코드 계산 + 조건 점검 + 승인 |
