### 응답 메타데이터·usage

- 응답 최상위 칸: `id`, `object`, `created`, `model`, `choices`, `usage`.
- `model`: 요청한 이름이 아니라 실제로 답한 버전 이름이 온다(예: `claude-sonnet-5.5`). 그래서 `LlmReply.model` 과 `llm_calls.model` 에는 실제 모델이 남는다.
- `usage` 칸: `prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_tokens_details{cached_tokens, cache_write_tokens, cache_write_tokens_details{ttl_5m_tokens, ttl_30m_tokens, ttl_1h_tokens}}`, `completion_tokens_details{reasoning_tokens}`. 이번 호출에서는 캐시·추론 토큰이 모두 0 이었다.
- **`usage.cost` 는 22번 모두 오지 않았다.** 그래서 `Usage.cost=None` 이고 `llm_calls.cost` 는 NULL 이다. 메모리 기록으로 확인했다: 22줄 모두 ok, cost 가 있는 줄은 0.
- 실제 도구 9개를 실으면 입력 토큰이 한 번에 약 2.8k(mark·gpt)~3.3k(gemini)~6.9k(claude) 늘어난다.

### 고칠 것

1. **배정 기본값은 지금 값을 유지한다.** light `liner-claude-router`/cost · normal `liner-claude-router`/balanced · hard `liner-claude-router`/quality · longdoc `liner-mark`/null. 네 모델(`liner-mark` 와 세 라우터) 모두 작은 도구와 실제 도구 전체로 도구 호출이 되므로 normal·hard 에서 빼야 할 모델이 없다. 다만 light/cost(haiku 로 갈 수 있음)로 `EXTRACT_SCHEMA` 를 부른 적은 없다. 이번에는 quality(sonnet)와 mark 에서만 확인했으므로 첫 실제 실행 때 본다.
2. **strict 스키마는 고칠 것이 없다.** `REPAIR_SCHEMA` 의 `wbs: anyOf[array, null]` 과 `EXTRACT_SCHEMA` 의 `["string","null"]`·`["integer","null"]`·`["array","null"]` 를 claude 라우터(quality)와 `liner-mark` 가 모두 400 없이 받았고, 답도 스키마에 맞았다. 실제 도구 스키마(pydantic `$defs`·`$ref`·`anyOf`·`oneOf`·`const`)도 네 모델이 모두 받았다. gpt·gemini 라우터에서 strict JSON 은 확인하지 않았으므로, 그쪽으로 배정을 바꾸면 다시 확인해야 한다.
3. **비용 표시**: `usage.cost` 가 오지 않으므로 지금 코드로는 화면과 기록의 비용이 늘 비어 있다. 비용을 보이려면 실제 답한 모델 이름(`model`)별 단가표로 토큰 수에서 계산하거나, Liner 콘솔 사용량을 따로 쓰는 방법이 있다. 둘 중 하나를 정해야 한다.
4. **`max_tokens`**: 앱 client 는 `max_tokens` 를 보내지 않는다(이번 실측에서만 더했다). `EXTRACT` 답이 sonnet 에서 845 토큰이었으니 WBS·초안처럼 긴 JSON 은 제공자 기본 상한에 맡기는 셈이다. 첫 실제 실행에서 답이 잘리지 않는지(`finish_reason` 이 `length` 가 아닌지) 보고, 쓰임새별로 상한을 줄지 정한다. 지금 client 는 `finish_reason` 을 기록하지 않는다.
5. **그림 입력**(묶음 3 참고용): `liner-mark` 와 claude 라우터 모두 data URI PNG 를 받고 색을 맞혔다. 같은 8×8 그림의 입력 토큰은 mark 1112, claude 51 로 크게 달랐다.
